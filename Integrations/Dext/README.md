# SwagDoc for Dext

Middleware that publishes the document generated by SwagDoc and a Swagger UI or Scalar page in an API written
with the [Dext](https://github.com/dotpas/dext) framework.

Dext has its own Swagger support, which writes an OpenAPI 3.0 document. This middleware reads the same
information that the application gives to Dext (the fluent API of the Minimal API endpoints, the attributes of
the controllers and the Swagger attributes of the types) and writes it with the object model of SwagDoc, so the
application keeps its code and gains what is listed below. Both can run side by side, at different routes, while
an application compares them.

## What changes compared with the Swagger support of Dext

Measured on the `SampleDextApi` demo, with the camelCase names and the enumerations by name configured in the
serializer of Dext:

| Subject                          | Swagger support of Dext                                   | SwagDoc                                                       |
| -------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------- |
| Specification                    | OpenAPI 3.0.0                                             | OpenAPI 3.2.1 (JSON Schema 2020-12) or Swagger 2.0            |
| When the document is generated   | When `UseSwagger` is called, so it must be the last call  | On the first request, so every endpoint is documented         |
| HTTP methods                     | GET, POST, PUT, DELETE and PATCH                          | Also HEAD, OPTIONS, TRACE and QUERY                            |
| Required properties              | `SwaggerRequired` is not written                          | Written in `required`                                          |
| Names of the properties          | As declared in Delphi, whatever the serializer writes     | As written by the serializer (`CaseStyle`, `JsonName`)         |
| Enumerations                     | Always by name, even when the serializer writes numbers   | As written by the serializer (`EnumStyle`)                     |
| Dates                            | `type: number`                                            | `type: string`, `format: date-time`, as the serializer writes  |
| Limits of lengths and values     | Not described                                             | `SwagLength` and `SwagRange` attributes                        |
| Rest of the document             | What the options of `UseSwagger` describe                 | The whole object model of SwagDoc, through `SwagDocApi`        |
| User interface                   | Swagger UI 5.10.0 from a CDN                              | Swagger UI 5.32.15 or Scalar 1.72.1, from a CDN, embedded or from a folder of the application |

The Swagger support of Dext is enough for an application that only needs an OpenAPI 3.0 document of its
endpoints. SwagDoc is for applications that need a Swagger 2.0 document, the current OpenAPI release, a document
that matches the JSON that the endpoints send, or the parts of the specification that Dext does not describe.

## Requirements

- A Delphi release supported by Dext, as listed in its compatibility matrix. SwagDoc itself needs Delphi XE7 or
  newer. Lazarus is not supported, because neither SwagDoc nor Dext support it.
- Dext 1.0.0 or newer, installed in the library path of the IDE, which is what TMS Smart Setup and the packages of
  Dext do.

## Installation

Add the following folders to the library path or to the search path of the project:

```
SwagDoc\Source
SwagDoc\Integrations\Dext\Source
```

## Quick start

```delphi
uses
  Dext.Web,
  Dext.SwagDoc;

var
  App: IWebApplication;
begin
  App := TDextApplication.Create;

  SwagDocApi.Info.Title := 'Pet Store';
  SwagDocApi.Info.Version := '1.0.0';
  TDextSwagDoc.Use(App.Builder);

  App.Builder.MapGet('/pets/{id}',
    procedure(Ctx: IHttpContext)
    begin
      Ctx.Response.Json('{}');
    end);

  App.Run(9000);
end.
```

The Swagger UI page is published in `http://localhost:9000/docs` and the document in
`http://localhost:9000/docs/openapi.json`. `TDextSwagDoc.Use` can be called before or after the endpoints are
registered, because the document is generated on the first request.

## Discovery of the endpoints

When the document is generated, every endpoint registered in Dext that is not documented yet is added to it with
what Dext knows about it:

- the summary, the description and the tags given by `SwaggerEndpoint.From(...)`, by the `With...` methods or by
  the `SwaggerOperation` and `SwaggerTag` attributes of the controllers;
- the request body, from the `RequestType` of a POST, PUT, PATCH or QUERY endpoint;
- the responses given by `.Response(...)` or by `SwaggerResponse`, with their schemas. When no successful response
  was given, a 200 response is written (201 for POST and 204 for DELETE) with the `ResponseType` of the endpoint;
- the security schemes given by `RequireAuthorization(...)` or by `[Authorize('scheme')]`. The `bearerAuth` scheme
  used by Dext is defined in the document when the application does not define it.

The path parameters are written as required strings, because Dext does not keep their types. The `Route` method
completes them, and any operation written by the application is kept as it is:

```delphi
uses
  Dext.SwagDoc,
  Swag.Common.Types;

var
  vPath: TSwagPath;
begin
  vPath := SwagDocApi.Route('/pets/{id}');
  vPath.Parameters[0].Description := 'The pet identifier';
  vPath.Parameters[0].TypeParameter := stpInteger;
end;
```

The discovery is disabled with:

```delphi
SwagDocConfig.DiscoverRoutes := False;
```

## Schemas of the types

The schemas of the request and response types are generated from the Delphi types by `TDextSwagSchemaBuilder`,
which follows the serializer of Dext:

- the names of the members follow the `CaseStyle` of `TDextJson.GetDefaultSettings`, and `JsonName` renames a
  member;
- the enumerations are written by name or by ordinal value, following the `EnumStyle` of the same settings;
- `JsonIgnore`, `NotMapped` and `SwaggerIgnoreProperty` leave a member out;
- `TDate`, `TTime` and `TDateTime` are written as date and time strings, which is what the serializer sends;
- `Prop<T>` is written as `T` and `Nullable<T>` as a `T` that also accepts null;
- the attributes `SwaggerSchema`, `SwaggerProperty`, `SwaggerRequired`, `SwaggerFormat` and `SwaggerExample` of
  Dext are honored, so the existing types need no change.

The attributes of SwagDoc, declared in `Swag.Doc.Schema.Attributes`, can be added to the same types and take
precedence. They also describe what the attributes of Dext do not:

```delphi
uses
  Dext.OpenAPI.Attributes,
  Swag.Doc.Schema.Attributes;

type
  [SwaggerSchema('Pet', 'A pet of the store')]
  TPet = record
    [SwaggerRequired, SwagLength(1, 60), SwaggerExample('Rex')]
    Name: string;

    [SwagRange(0, 150)]
    Weight: Double;
  end;
```

## Settings

The settings must be defined before the first request.

```delphi
SwagDocConfig.UserInterfaceRoute := '/api-docs';
SwagDocConfig.DocumentRoute := '/api-docs/swagger.json';
SwagDocConfig.UserInterfaceTitle := 'Pet Store';
SwagDocConfig.UserInterfaceResources := '/swagger-ui';
SwagDocConfig.DefaultSecurityScheme := 'bearerAuth';

TDextSwagDoc.Use(App.Builder);
```

The routes of the page and of the document can also be given to the middleware:

```delphi
TDextSwagDoc.Use(App.Builder, '/api-docs', '/api-docs/openapi.json');
```

| Property                 | Default value             | Description                                                              |
| ------------------------ | ------------------------- | ------------------------------------------------------------------------ |
| `UserInterfaceRoute`     | `/docs`                   | Route of the page                                                         |
| `DocumentRoute`          | `/docs/openapi.json`      | Route of the generated document                                           |
| `UserInterface`          | `uiSwaggerUi`             | Interface that renders the document: `uiSwaggerUi`, `uiScalar`            |
| `UserInterfaceTitle`     | The title of the document | Title of the page                                                         |
| `UserInterfaceResources` | Embedded files or a CDN   | Base address of the files of the interface                                |
| `DiscoverRoutes`         | `True`                    | Documents the registered endpoints that are not documented yet            |
| `DefaultSecurityScheme`  | Empty                     | Scheme written for controllers marked with `[Authorize]` without a scheme |

The routes are compared with the path of the request after the `PathBase` of the application is removed, and the
page builds its addresses with `ToAppUrl`, so the documentation works under a path base.

## Swagger 2.0

The document created by the middleware is written as an OpenAPI 3 document. Applications that publish a
Swagger 2.0 document define the specification version, the address of the API, which Swagger 2.0 does not take
from the servers, and usually the route of the document:

```delphi
SwagDocConfig.DocumentRoute := '/docs/swagger.json';
SwagDocApi.SpecVersion := svSwagger2;
SwagDocApi.Host := 'localhost:9000';
```

The document created by the middleware has the `OmitEmptyBasePath` property set to True, so the `basePath` field
is only written when the `BasePath` property is defined. A document given with `SetSwagDocApi` keeps its own
setting.

## User interface

The document is rendered by Swagger UI, the default, or by Scalar:

```delphi
SwagDocConfig.UserInterface := uiScalar;
```

## Where the files of the interface come from

By default the page loads the files of the selected interface from a public CDN, so nothing is embedded in the
executable. There are two other ways to publish them.

**Embedded in the application.** Declare the conditional define of the interface in the options of the project,
under *Conditional defines*, and the files are linked into the executable and published under the route of the
page. They are embedded compressed with gzip and decompressed once, on the first request of each file.

| Conditional define                 | Interface  | Size added to the executable |
| ---------------------------------- | ---------- | ---------------------------- |
| `DEXT_SWAGDOC_EMBEDDED_SWAGGER_UI` | Swagger UI | about 510 KB                 |
| `DEXT_SWAGDOC_EMBEDDED_SCALAR`     | Scalar     | about 1.2 MB                 |

Both defines can be declared together, and the interface is still selected at runtime. When the selected
interface is not the embedded one, its files are loaded from the CDN. The licenses of the embedded files are in
the `Resources` folder and must be kept with the distribution of the application.

**Copied to a folder of the application.** Copy the files of the interface to a folder published by the static
files middleware of Dext and point the settings to it. The files are the ones of `Deploy\OpenApi3`
(`swagger-ui.css`, `swagger-ui-bundle.js` and `swagger-ui-standalone-preset.js`) or of `Deploy\OpenApi3-Scalar`
(`standalone.js`):

```
www\swagger-ui\swagger-ui.css
www\swagger-ui\swagger-ui-bundle.js
www\swagger-ui\swagger-ui-standalone-preset.js
```

```delphi
App.Builder.UseStaticFiles('www');
SwagDocConfig.UserInterfaceResources := '/swagger-ui';
```

## Using a document built by the application

Applications that already build their own document give it to the middleware, which does not destroy a document
that it does not own:

```delphi
SetSwagDocApi(fSwagDoc);
```

## Generation of the document

The document is generated on the first request and kept in memory. Applications that change the document while
they are running discard the generated one with:

```delphi
ClearSwagDocApiCache;
```

## What Dext does not tell

The discovery writes what Dext keeps about each endpoint, and some information is not kept:

- the types of the path parameters, completed with `SwagDocApi.Route`;
- the query parameters of a GET endpoint that binds a record, since Dext only keeps the request type of the
  endpoints with a body;
- the scheme of a controller method marked with `[Authorize]` without a name, written with
  `DefaultSecurityScheme` only when the controller itself is marked;
- the `operationId` given to `SwaggerOperation`.

Each of them can be written by the application in `SwagDocApi`, since the operations already in the document are
never replaced by the discovery.
